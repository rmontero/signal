# Verification matrix

This matrix is the release acceptance plan for MVP-01 through MVP-15. Until the application and scripts exist, every check is `NOT RUN`; a script name documents the intended entry point and does not imply implementation. A passing build or unit suite cannot substitute for a real integration smoke test. Evidence should contain IDs, hashes, status, duration, and URLs where safe; it must not contain source text, prompts, secrets, or complete task payloads.

| ID | Scenario and expected result | Initial status |
|---|---|---|
| MVP-01 | Send an ordinary message, a bot message, and an explicit `@Signal` mention. Only the mention creates an analysis request. | NOT RUN |
| MVP-02 | Invoke a paginated thread at the 50-message limit, then one with a missing page and one over the limit. Complete input may propose; missing or overflow input withholds execution and explains why. | NOT RUN |
| MVP-03 | Use a synthetic thread containing a decision, task, owner, blocker, deadline, and an absent fact. Each present assertion has source evidence; the absent fact is omitted. | NOT RUN |
| MVP-04 | Map one channel to one repository and return mixed issue/PR search results. At most five valid candidates from that repository appear; an unconfigured model-selected repository is rejected. | NOT RUN |
| MVP-05 | Open the action card and review modal. Destination, exact title/body or comment, assignee, uncertainty, sources, and analysis time match the persisted draft. | NOT RUN |
| MVP-06 | Try approval with a wrong tenant/channel, unknown actor, expired proposal, superseded version, and changed payload. Each is denied without state change; a named approver can approve the exact live draft. | NOT RUN |
| MVP-07 | Approve a create draft. Exactly one issue is created with the immutable body marker, returned URL/ID, and returned assignee; no post-approval model call occurs. | NOT RUN |
| MVP-08 | Approve an update draft. Exactly one comment is added to the validated open issue; existing title, body, state, and assignees remain unchanged. | NOT RUN |
| MVP-09 | Supply a mapped person, an unmapped person, and an ambiguous display name. Only the explicit mapping is assigned; the others remain unassigned with an explanation. | NOT RUN |
| MVP-10 | Replay the same Slack delivery, click approval twice, and start the same execution task twice. Inbox, approval, and task keys deduplicate; GitHub has one mutation. | NOT RUN |
| MVP-11 | Crash between acceptance and dispatch; return an unknown create or comment response. Outbox recovery dispatches once, and unknown writes reconcile by stable marker before any action. An expired `SENDING` lease is recoverable only when the owning Trigger attempt/run is confirmed terminal and has no continuing retry attempt. | NOT RUN |
| MVP-12 | Make GitHub succeed and Slack result notification fail, then retry notification. The persisted result is reused and GitHub is never repeated. | NOT RUN |
| MVP-13 | Attempt every cross-tenant proposal, repository, issue, approval, and outbox lookup with a foreign tenant ID. Compound keys and execution checks fail closed. | NOT RUN |
| MVP-14 | Send source at each configured limit, an injection-shaped instruction, malformed AI JSON, and provider timeout. Limits hold, model text cannot authorize a write, sensitive material is absent from logs, and the proposal is withheld or queued safely. | NOT RUN |
| MVP-15 | Run setup, recovery, demo, and this matrix from a clean environment. Commands and results are recorded truthfully; missing credentials or optional integrations leave a documented disabled state. | NOT RUN |

The focused security and recovery cases are deliberately repeated in the implementation suites: duplicate Slack deliveries/clicks/task starts; forged callback signatures and forged approval payloads; expired and superseded approvals; tenant-boundary reads and execution; source overflow; prompt injection and malformed or missing AI output; missing identity; response loss for both `CREATE_ISSUE` and `ADD_PROGRESS_COMMENT`; crash gaps; Slack-only retry; accepted-but-assignee-dropped responses; and an active `SENDING` lease. The lease case must require both an expired lease and confirmed terminality of the owning Trigger attempt/run with no continuing retry attempt. An expired lease whose owner is still running remains blocked and must produce no POST, transition, or reconciliation. An `UNKNOWN` operation with no matching marker remains `UNKNOWN`; it must never resend a POST merely because a read found no marker.

The evaluation corpus has at least 20 synthetic fixtures across these categories: explicit create task; explicit progress update; decision without task; blocker; deadline with timezone; ambiguous deadline; missing owner; ambiguous owner; unmapped owner; multiple candidate issues; no related result; PR mention that is not an issue target; multiple explicit targets; closed issue; transferred issue; inaccessible repository; source pagination gap; source overflow; bot-only thread; and injection/malformed model response. Extraction acceptance is at least 90% for required facts over the corpus, with evidence attached to each scored assertion and no invented values. Fixtures contain names such as Carlos and Ana but no production data.

Future commands are the following npm scripts, to be defined by the implementation package. Until code exists each is `NOT IMPLEMENTED`, regardless of configuration or CI flags: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run test:integration`, `npm run test:eval`, `npm run test:e2e`, and `npm run build`. The documentation link/contract check is tracked separately. A final report must distinguish unit, mocked integration, real Slack/GitHub smoke, evaluation, browser E2E, and build evidence.
