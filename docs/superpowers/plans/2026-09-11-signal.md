# Signal Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development for coordinated task execution. The user's `AGENTS.md` and `tasks.md` rules take precedence over generic skill bookkeeping. One active task per worker; no overlapping edits.

**Goal:** Deliver the required Slack → approved GitHub issue/comment workflow, then a verified two-minute demo, while attempting useful partner additions only within the timebox.

**Architecture:** Next.js HTTP handlers durably accept signed Slack requests into PostgreSQL. Trigger.dev tasks analyze scoped evidence, persist immutable proposals, execute approved actions, reconcile uncertain outcomes, and update Slack. PostgreSQL is the source of truth for tenant scope, approval and mutation state.

**Tech stack:** Node.js 24, TypeScript, npm, Next.js App Router, Neon PostgreSQL, Drizzle, Trigger.dev, OpenRouter routing OpenAI, Slack Web API, GitHub App. Optional Auth0, CopilotKit, Exa, Ambiguous AI, Mozilla.ai.

**Spec:** [north_star.md](../../../north_star.md), [PRODUCT.md](../../PRODUCT.md), [CONTRACTS.md](../../CONTRACTS.md). Current work: [tasks.md](../../../tasks.md).

**Execution model:** the user's selected affordable model. Astra planning/review is complete; AGENTS prohibits automatic Astra escalation. Break each task into one verifiable substep per loop, with fresh-context review for critical behavior. Resume through [HANDOFF.md](../../HANDOFF.md).

## Global constraints

- Target four hours of coding followed by two hours of verification/polish/demo/documentation. Record the implementation start once; do not restart the clock after failures.
- The only MVP GitHub writes are `CREATE_ISSUE` and `ADD_PROGRESS_COMMENT` after named Slack approval.
- Only a verified Slack interaction can approve a GitHub operation. The optional web inspector is read-only.
- Use one inference adapter via OpenRouter and one task engine, Trigger.dev. Do not add Vercel Workflows or a second Gateway route.
- Use the exact limits and default behavior in PRODUCT. Optional features cannot break the required flow when disabled.
- Typed contracts and transitions in CONTRACTS bind every worker. The coordinator owns shared types and package/lock changes.
- Every task ends with relevant verification and review. Report actual evidence; a mocked provider response is not a live integration.

## Repository layout and ownership

One repository with `src/app` route handlers/pages, `src/domain` types and policy, `src/db` schema/migrations/access, `src/adapters` provider clients, `src/services` application behavior, `src/trigger` tasks, `src/components` presentation, `tests` fixtures and checks, and `scripts` developer operations. Keep handlers thin and application policy out of UI components.

No monorepo, additional production runtime, or generalized plugin platform. Tests use injected adapter boundaries for deterministic failures and a real isolated Postgres database for transactions. The production path must use actual providers; test fixtures cannot be an automatic runtime fallback.

## I-02 — Tenant-aware persistence and application contracts (worker + reviewer)

**Consumes:** CONTRACTS. **Produces:** migrations, tenant-scoped data access, atomic inbox/outbox and operation transitions. **Owned files:** `src/domain/*`, `src/db/*`, `tests/integration/persistence.test.ts`.

- [ ] Encode the contract discriminated unions and validation schemas. Reject unsupported action types, missing tenant IDs and invalid resource relationships.
- [ ] Create tables, compound tenant/object foreign keys, deduplication constraints, active-proposal constraints and thread links exactly as documented. Use a separate migration connection/role from application access.
- [ ] Implement atomic event acceptance + dispatch, approval + execution dispatch, and successful external result + notification dispatch.
- [ ] Implement conditional state updates and claim leases. Concurrent workers cannot both obtain mutation authority. An active SENDING operation cannot be reclaimed as a fresh send.

**Verify:** `npm run test:integration -- tests/integration/persistence.test.ts`, then `npm run typecheck`. **Done:** database invariants hold under concurrent attempts; later workers consume fixed interfaces without inventing alternate state stores.

**Verify:** focused unit tests and a deployed signed-event smoke test; measure acknowledgement under three seconds. **Done:** a real mention creates one durable analysis job and full thread context.

## I-05 — Human approval and deterministic GitHub actions (worker + reviewer)

**Consumes:** exact Proposal and operation contract. **Produces:** an authorized create/comment attempt and persisted result. **Owned files:** Slack interaction route/modal rendering, `src/services/approve.ts`, `src/services/execute.ts`, GitHub mutation adapter, `tests/approval.test.ts`, `tests/execution.test.ts`.

- [ ] Open the full read-only review modal promptly using the Slack interaction token. The modal submission, not opening the card, approves the draft.
- [ ] Verify signature, tenant, channel, named actor, pending version/hash, current policy, target and expiry. Dismissal is terminal for that proposal; invalid clicks cannot change shared state.
- [ ] Commit approval and execution dispatch together. Recheck current policy and target eligibility in the executor; stale or inaccessible targets do not execute.
- [ ] Atomically acquire mutation authority with READY → SENDING and record the owning attempt. Send the exact persisted payload once, with provider SDK mutation retries disabled.
- [ ] Save actual external IDs and returned assignees. Distinguish definite rejection from uncertain network/server outcomes. Never run the model after approval.
- [ ] Run real create and add-progress-comment paths on the authorized demo repository; do not change existing issue fields.

**Verify:** focused authorization, tenant, expiry, mismatch, double-click and action tests; inspect resulting real issue/comment. **Done:** neither frontend tools nor a model can bypass the Slack approval transition.

## I-06 — Reconciliation and result delivery (worker + reviewer)

**Consumes:** operation/outbox contracts and GitHub result records. **Produces:** safe recovery and Slack confirmation. **Owned files:** `src/services/reconcile.ts`, `src/services/notify.ts`, maintenance endpoint, remaining Trigger tasks, `tests/recovery.test.ts`.

- [ ] Replayed active SENDING returns in-progress. A stale/terminated attempt becomes reconciliation work, never a fresh POST. Honor the owning-attempt fencing rule from CONTRACTS.
- [ ] Reconcile issue creation via repository issue listings and comment creation via that issue's comments. Verify marker, expected app author, target and approved payload; support pagination and rate-limit waits.
- [ ] One valid result completes the operation; multiple matches flag an anomaly; absence remains UNKNOWN with an operator resolution note. Do not reset idempotency keys or resend based on absence.
- [ ] Commit successful GitHub result + notification outbox atomically. Update the original Slack card by stored message timestamp. Failures retry notification only.
- [ ] Add scheduled pending-outbox recovery and retention cleanup, using ID-only task payloads and redacted errors. Handle expired leases without granting duplicate mutation authority.
- [ ] Remove the temporary `signal.preflight` task after real business-task acceptance replaces its connectivity-only evidence.
- [ ] Test dispatch-before/after crash windows, active send contention, accepted POST with lost response for both actions, crash before POST, delayed completion, notification failure and ambiguous reconciliation.

**Verify:** focused recovery tests, DB integration checks and a live replay proving no duplicate issue/comment. **Done:** the required MVP is eligible for feature freeze once remaining core checks pass.

## Optional work — only after the core gate

- **O-01, Auth0:** implement one read-only inspector. Explicitly map Auth0 subjects to tenant IDs; enforce the mapping on every endpoint and omit workspace data from unauthenticated responses. No sending mail/chat or writing documents/tasks; count a successful, useful read with evidence.
- **O-05, Mozilla.ai:** use the documented evaluation tooling on synthetic exported run data. Keep it offline and optional; no production Python service, no private trace export, no rewrite of the application agent. Count a completed evaluation result, not a dependency installation.

Verify actual behavior and disabled-feature boot/build. If a task cannot fit its slot or depends on unavailable access, record DEFERRED and continue the core/finishing work.
